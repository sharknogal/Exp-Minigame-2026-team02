# 공 8종 능력과 블록 상호작용 구현 계획

작성일 2026년 10월 7일 · 대상 Unity 6000.5.10f1 · 구현 작업 예산 120분

오늘의 목표는 **일반공을 포함한 공 8종의 피해와 추가 효과를 팀원의 블록 코드에 연결하고, 공을 움직이지 않고 검증하는 것**이다. 공의 이동, 물리 충돌 판정, 반사와 관통 동작은 후속 작업으로 둔다.

2026년 10월 7일 구현과 Unity Play 모드 자동 검증 40개를 완료했다. 실제 파일 구성과 실습 방법은 [코드 읽기 안내](BallEffectsReadingGuide.md), 사례별 결과는 [검증 기록](BallEffectsTestResults.json)을 참고한다. 아래 내용은 구현에 사용한 설계와 완료 기준이다.

적중 처리의 시작점을 `ApplyHit` 함수로 정한다. 오늘은 테스트 메뉴가 이 함수를 호출하고, 나중에는 실제 충돌 코드가 같은 함수를 호출한다. 효과 처리에서 Rigidbody2D, 충돌 콜백, 공의 위치와 속도를 참조하지 않으면 이동 구현을 뒤로 미뤄도 효과 코드를 다시 작성할 필요가 없다. 이후 실제 접촉 중복, 고속 충돌, 반사와 관통을 검증하는 통합 작업은 별도로 필요하다.

## 1 오늘의 범위

| 오늘 구현할 항목 | 완료 기준 |
| --- | --- |
| 공 8종의 직접 피해와 추가 효과 | 지정한 블록에 적중을 입력하면 기획서에 맞게 체력이 변한다 |
| 격자 조회 연결 | 블록의 행과 열, 특정 칸의 살아 있는 블록을 조회한다 |
| 실제 피해량 계산 | 남은 체력을 초과한 피해를 게이지 충전량에서 제외한다 |
| 레이저의 공별 발동 상태 | 같은 발사 구간에서는 공 하나당 첫 유효 적중에만 발동한다 |
| 화염 예약 관리 | 지연 피해, 중첩, 대상 파괴와 발사 구간 종료 시 취소를 검증한다 |
| 결과 전달 | 즉시 효과 후 대상 파괴 여부, 피해 내역, 게이지 증가량과 콤보 증가량을 제공한다 |
| 테스트 씬과 실행 메뉴 | 일반 블록을 고정 배치하고 원하는 공과 대상 칸을 골라 적중시킨다 |

후속 작업은 공 이동, Collider2D를 통한 실제 충돌 감지, 반사와 관통, 속도 증가, 조준, 발사 간격과 자연 회수, 완성형 공 프리팹, 시각 효과와 사운드다. 골드 지급, 공유 게이지 600 도달 시 특수 능력 발동, 구매와 턴 진행도 이번 구현 범위에 포함하지 않는다. 이번에는 이 시스템들이 받을 결과를 준비한다.

**공 프리팹 8개를 먼저 만들 필요는 없다.** 오늘의 테스트는 공 종류를 데이터로 선택한다. 실제 공 프리팹을 만들 때 공 종류와 적중 함수 연결을 붙인다. 일반공은 추가 효과가 없는 기준 동작으로 함께 구현한다.

## 2 현재 프로젝트의 연결 대상

구현 시작 시 로컬 프로젝트의 게임용 스크립트는 `Block.cs`와 `GridManager.cs`였다. 저장된 `SampleScene`에는 `Board`, 좌우 벽과 천장, `Blocks`, `GridManager`, `Ball`, 카메라, 조명, Canvas와 EventSystem이 있다. 기존 `Ball`에는 Transform과 SpriteRenderer만 있고 물리 컴포넌트와 공 스크립트는 없다. 시작 당시 에디터에 열린 씬은 Main Camera만 있는 미저장 씬이었다.

`Block` 프리팹에는 SpriteRenderer, 0.92 × 0.92 크기의 BoxCollider2D, 체력 텍스트와 Block 컴포넌트가 있다. 프리팹의 저장된 체력은 21이다. `GridManager`의 블록 프리팹과 부모 연결은 저장된 SampleScene에 설정되어 있다.

### 팀원 코드를 수정하지 않는 연결 방식

`Block.cs`의 `Initialize`, `TakeDamage`, 체력과 파괴 처리는 그대로 사용한다. 공이 체력을 별도로 보관하거나 오브젝트를 직접 삭제하지 않는다. 팀원의 공개 함수 서명도 유지한다.

`Block.cs`, `GridManager.cs`, 기존 Block 프리팹과 SampleScene은 수정하지 않는다. 공 담당 폴더의 새 `BallBoardLookup.cs`가 다음 조회 함수를 제공한다. 초기 계획의 GridManager 함수 추가 방식은 협업 조건에 맞춰 이 방식으로 변경했다.

```csharp
public Block GetBlock(int row, int column);
public bool TryGetCell(Block block, out int row, out int column);
```

- 외부 행은 위부터 1~8, 열은 왼쪽부터 1~6을 사용한다.
- 초기화는 `effects.Configure(grid, blocksParent)`로 한다. `blocksParent`에는 해당 보드의 블록만 들어 있는 부모 Transform을 전달한다.
- `GetBlock`은 이 부모 아래의 활성 Block을 찾고, 월드 XY 위치를 공개 함수 `GridManager.GetCellPosition`의 결과와 비교한다. 허용 오차는 0.001 Unity 단위다. private 배열을 읽거나 수정하지 않는다.
- 범위 밖, 빈칸, 비활성/파괴된 블록은 null이다. 같은 칸에 두 블록이 겹치면 임의의 블록을 선택하지 않고 null로 처리한다.
- `TryGetCell`은 8 × 6칸의 좌표와 비교한다. 연결한 부모 밖의 대상, 격자 칸 사이에 있는 대상, 중복된 칸은 false다.
- 조회할 때 현재 자식을 다시 읽으므로 생성/삭제/재배치를 별도 좌표 목록과 동기화할 필요가 없다. Physics2D 검색과 Reflection은 사용하지 않는다.
- 블록 하강 중에는 적중을 보내지 않고, 정확한 칸에 배치된 뒤 발사를 시작한다. 나중에 이동 중에도 피해가 필요하거나 격자 규격이 달라지면 이 연결 파일을 보완한다. GridManager 내부 배열의 관리 책임은 블록 담당자에게 있다.

현재 `TakeDamage`는 이미 파괴된 블록에도 true를 반환한다. 따라서 호출 전에 대상 생존 여부를 검사해야 중복 파괴 보고와 중복 충전이 발생하지 않는다. 파괴 시 실제 삭제가 프레임 끝에 이루어지더라도 `IsDestroyed`를 즉시 확인해 후속 피해에서 제외한다.

## 3 구현 구성

프로젝트 루트를 기준으로 다음 위치를 계획했다. 실제 구현에서는 읽기 쉽도록 피해 결과를 `BallDamageReport.cs`, 범위 효과를 `BallAreaEffects.cs`, 화염 예약을 `BallFireScheduler.cs`로 분리했다. 검증 코드와 Inspector 버튼도 Testing 폴더에서 별도 파일로 구분했다.

| 예정 파일 | 역할 |
| --- | --- |
| `Assets/_Project/Scripts/Balls/BallEffectTypes.cs` | 공 종류, 공별 상태, 적중 결과와 피해 기록 자료형 |
| `Assets/_Project/Scripts/Balls/BallDamageService.cs` | Block.TakeDamage 호출, 실제 피해와 파괴 전후 정보 계산 |

| `Assets/_Project/Scripts/Balls/Testing/BallEffectTestHarness.cs` | 고정 블록 배치, 적중 메뉴, 결과 표시와 검증 실행 |

8종마다 별도 클래스를 만들지 않고 공 종류 열거형과 효과별 메서드로 시작한다. 직접 피해는 공통 경로에서 한 번 적용하고, 효과별 메서드는 추가 효과만 처리한다. 이는 폭발 중심에 직접 피해가 두 번 들어가는 실수를 막는다.

컨트롤러는 개별 공 오브젝트와 독립된 씬 오브젝트에 둔다. 공이 회수되거나 나중에 풀로 반환되어 비활성화돼도, 전체 발사 구간이 진행 중이면 화염 예약을 유지할 수 있어야 한다.

## 4 외부에서 호출할 함수

다음 서명을 연결 계약으로 사용한다. `shotId`는 모든 공이 함께 참여하는 발사 구간 번호, `ballId`는 그 구간 안에서 개별 공을 구분하는 번호다. 같은 종류의 공 두 개도 서로 다른 ballId를 사용한다.

```csharp
void Configure(GridManager grid, Transform blocksParent, int? randomSeed = null);
void BeginShot(int shotId);
bool RegisterBall(int shotId, int ballId, BallEffectType type, int attackPower);
HitResult ApplyHit(int shotId, int ballId, Block target);
void EndShot(int shotId);
event Action<DamageBatch> DamageBatchCompleted;
```

### 발사 구간과 공 상태

1. `BeginShot`으로 공통 발사 구간을 연다. 새로운 번호이면 이전 구간의 화염 예약과 공 상태를 정리한다. 같은 번호를 중복 호출해 레이저 상태를 다시 초기화하지 않는다.
2. 각 공을 `RegisterBall`로 한 번 등록한다. 종류, 공격력과 첫 적중 여부는 공별로 보관한다. 중복 등록과 잘못된 구간 번호는 거부한다.
3. 유효한 `ApplyHit` 한 번을 실제 블록 직접 적중 한 번으로 취급한다. 한 공이 같은 블록을 나중에 다시 때리는 것은 정상적인 새 적중이다.
4. `EndShot`은 전체 구간의 남은 화염 예약을 취소하고 구간을 닫는다. 이미 닫힌 구간에 대한 중복 호출은 아무 효과가 없어야 한다.

공격력은 등록 시점의 값을 사용한다. 호출자는 기획서의 `10 + 2 × 공격력 업 획득 횟수`를 전달한다. 정상 값은 10 이상의 짝수이며, 잘못된 값은 등록 단계에서 거부한다. 조준 단계의 구매와 강화가 끝난 뒤 등록하는 흐름을 전제로 한다.

### 유효하지 않은 적중

종료된 구간, 미등록 공, null 또는 파괴된 대상, 연결한 부모 밖의 대상이나 칸에 정확히 놓이지 않은 대상은 `HitResult.IsValid = false`로 반환한다. 피해, 콤보, 게이지, 화염 예약과 레이저 첫 적중 상태를 바꾸지 않는다.

현재 계층은 실제 충돌을 감지하지 않으므로 같은 접촉에서 발생한 중복 콜백을 구분하지 않는다. 후속 충돌 코드는 직접 적중 하나에 `ApplyHit`을 한 번만 호출해야 한다. 블록별 영구 중복 금지를 넣으면 정상적인 재충돌도 막히므로 그렇게 구현하지 않는다.

### 적중 결과

| 값 | 의미 |
| --- | --- |
| `IsValid` | 적중 요청이 유효했는지 |
| `DirectTargetDestroyed` | 직접 피해와 즉시 효과가 끝난 시점에 처음 맞은 블록이 파괴됐는지 |
| `ImmediateActualDamage` | 이번 적중에서 지금까지 즉시 적용한 실제 피해 합계 |
| `ImmediateGaugeCharge` | 위 피해로 발생한 게이지 증가량 |
| `ComboDelta` | 유효한 직접 적중이면 1, 무효이면 0 |

화염의 미래 피해는 이 반환값에 미리 합산하지 않는다. 각 예약 피해가 실제 적용된 시점에 `DamageBatchCompleted`로 별도 보고한다. 반환값은 호출자의 동작 판단용이고, 게이지와 보상 누적은 이벤트에서 한 번만 처리해 이중 집계하지 않는다.

## 5 직접 피해와 추가 효과의 처리 순서

1. 구간, 공, 대상과 격자 등록 상태를 검증한다.
2. 블록이 사라지기 전에 대상의 행과 열을 확보한다.
3. 공통 피해 함수를 통해 대상에 직접 피해 A를 한 번 적용한다.
4. 공 종류와 첫 적중 여부에 따라 즉시 추가 효과를 적용하거나 화염 피해를 예약한다.
5. 대상의 최종 생존 여부와 이번 즉시 피해 묶음을 확정한다.
6. 확정한 피해 묶음을 한 번 보고한 뒤 적중 결과를 반환한다. 보고를 받는 상위 시스템은 파괴 보상, 게이지 충전, 능력 발동 순서로 처리한다.

효과별 함수는 직접 적중 진입점을 다시 호출하지 않는다. 추가 피해는 `BallDamageService`만 거친다. 이렇게 해야 추가 피해가 다른 공 효과, 콤보 또는 이후 공 가속을 재발동시키지 않는다.

### 실제 피해와 파괴 기록

피해 적용 전 현재 체력, 최대 체력, 골드 속성, 대상 칸을 확보한다. `TakeDamage(amount)` 호출 후 실제 감소한 체력을 계산한다. 실제 피해는 0 이상이며 적용 전 체력을 넘지 않는다.

예를 들어 체력 3인 블록에 공격력 10으로 공격하면 실제 피해는 3이다. 일반공의 충전 기여는 3, 충전공은 6이다. 체력이 0이 된 블록에 들어가는 후속 피해는 0이며 추가 파괴를 보고하지 않는다.

각 피해 기록에는 구간과 공 번호, 공 종류, 대상 칸, 직접 또는 추가 피해 구분, 요청 피해, 실제 피해, 충전 기여량과 이번 피해로 새로 파괴됐는지를 포함한다. 파괴 기록에는 최대 체력과 골드 속성도 복사한다. 다른 담당자가 삭제된 GameObject를 다시 조회하지 않고 보상을 계산할 수 있게 하기 위해서다.

`DamageBatch`는 한 직접 적중의 직접 피해와 즉시 효과를 묶거나, 화염 예약 한 회의 피해를 묶는다. 콤보는 직접 적중 묶음에만 1을 기록한다. 특수 능력 등 다른 피해 원인은 나중에 이 보고를 사용하더라도 공 효과 진입점을 호출하지 않는다.

## 6 공 8종의 정확한 규칙

모든 종류는 직접 충돌 대상에 공격력 A를 먼저 적용한다. 아래에서 범위는 적중한 블록의 칸을 기준으로 한다. 필드 밖과 빈칸을 건너뛰고 이미 파괴된 블록은 공격하지 않는다.

| 종류 | 추가 효과 | 발동과 중복 규칙 |
| --- | --- | --- |
| 일반공 | 없음 | 매 유효 직접 적중에 A만 적용 |
| 폭발공 | 중심을 제외한 3 × 3 범위의 최대 8칸에 A/2 | 매 적중 발동. 중심에 추가 피해 없음 |
| 감전공 | 직접 피해 후 5 × 5 범위의 다른 생존 블록 최대 3개에 각각 A | 중심 제외. 중복 선택 금지. 후보가 3개보다 적으면 모두 공격 |
| 가로 레이저공 | 해당 행 전체에 A/2 | 그 공의 구간 내 첫 유효 적중에만 발동. 중심이 살아 있으면 포함 |
| 세로 레이저공 | 해당 열 전체에 A/2 | 그 공의 구간 내 첫 유효 적중에만 발동. 중심이 살아 있으면 포함 |
| 십자 레이저공 | 가로와 세로 레이저를 각각 적용 | 첫 유효 적중에만 발동. 중심은 살아 있으면 두 방향에서 각각 A/2를 받아 직접 피해 포함 최대 2A |
| 화염공 | 같은 블록에 적중 0.15초, 0.30초, 0.45초 후 각각 A | 매 적중마다 3회 예약. 기존 예약을 덮어쓰지 않음 |
| 충전공 | 해당 직접 피해의 실제 체력 감소량을 2배로 충전 보고 | 직접 피해 자체는 A. 초과 피해 제외 |

폭발, 감전과 레이저는 직접 피해로 중심 블록이 파괴되어도 기억한 칸을 기준으로 발동한다. 십자 효과를 행과 열의 합집합으로 중복 제거하면 중심 추가 피해가 한 번 빠지므로 두 방향을 따로 처리한다.

레이저 공은 첫 유효 블록 적중을 처리할 때 상태를 사용 완료로 바꾼다. 첫 적중에서 주변 대상이 없더라도 효과 사용을 소비한다. 다른 레이저 공의 상태에는 영향을 주지 않는다.

### 화염 예약의 수명

화염은 각 적중 당시의 대상 참조, 공격력과 구간 번호를 예약에 저장한다. 새 블록이 나중에 같은 칸에 생성돼도 이전 블록의 예약 피해를 받지 않는다. 여러 번 적중한 예약은 독립적으로 누적한다.

예약 실행 직전에 구간 유효성과 대상 생존을 다시 검사한다. 대상이 파괴되면 해당 대상의 남은 피해를 중단한다. `EndShot`이나 새 구간 시작 시 이전 구간의 예약을 모두 취소한다. 공 하나의 회수나 비활성화만으로는 전체 구간을 종료하지 않는다.

시간은 게임 시간으로 계산한다. 일시정지 시 지연 피해도 멈춘다. 실행 시각은 0.15초 간격의 목표 시각 이후 첫 실행 가능한 프레임이므로 검증에 프레임 오차를 허용한다. 피해 효과를 기다리느라 다른 공의 적중을 막지 않는다.

## 7 테스트 씬의 사용 흐름

테스트 씬에는 기존 Block 프리팹과 GridManager를 연결하고, 움직이는 공 없이 효과 컨트롤러와 테스트 하네스를 둔다. 별도 씬을 사용해 팀원의 SampleScene을 실험용으로 변경하지 않는다.

Inspector에서 공 종류, 공격력, 공 번호, 대상 행과 열을 선택한다. 아래 ContextMenu는 Play 모드에서만 동작하도록 한다.

| 메뉴 | 동작 |
| --- | --- |
| `Prepare Fixture` | 기존 발사 구간을 종료하고 테스트 블록을 고정 배치 |
| `Begin Test Shot` | 새로운 구간 번호로 시작 |
| `Register Test Ball` | 선택한 공 번호와 종류, 공격력 등록 |
| `Apply Hit` | 선택한 칸의 블록에 적중 요청 |
| `End Test Shot` | 남은 화염 예약을 취소하고 구간 종료 |
| `Run All Cases` | 각 사례의 배치를 새로 준비하며 기대값과 결과를 비교 |

기본 배치는 2~7행과 1~6열 전체에 일반 블록 체력 100, 공격력 10, 중심 칸 4행 3열이다. 기본 체력이 낮은 `Test Spawn Turn 1` 대신 고정 배치를 사용해야 추가 피해량을 분명히 확인할 수 있다.

배치 초기화 시 테스트용 GridManager와 자식 블록을 정리하고 파괴가 반영된 다음 프레임에 다시 만든다. 팀원의 private 배열을 강제로 수정하거나 같은 프레임에 파괴된 슬롯을 즉시 재사용하지 않는다. Console에는 사례 이름, 기대값, 실제값과 성공 여부를 출력하고 씬의 체력 텍스트도 함께 확인한다.

| 시간 | 구현 작업 | 해당 단계의 완료 기준 |
| --- | --- | --- |
| 0~15분 | 격자 조회 함수, 공 종류와 결과 자료형 | 기존 블록 생성과 피해 테스트 유지, 외부 칸 조회 가능 |
| 15~35분 | 공통 피해 경로, 구간과 공 등록, 일반공 | 직접 피해, 실제 피해, 파괴와 무효 입력 처리 검증 |
| 35~60분 | 폭발, 감전, 레이저 3종 | 대상 선정, 중심 처리와 첫 적중 상태 검증 |

시간이 부족해도 실제 피해량, 첫 적중 초기화, 중심 파괴 후 범위 효과와 화염 취소 검증은 유지한다. 메뉴 편의 기능과 추가 시각 연출부터 후속 작업으로 넘긴다. 문서의 검증 표는 완료 여부를 판단하는 기준으로 사용하며 실제 실행 전에는 통과로 표시하지 않는다.

## 10 나중에 이동과 충돌을 연결하는 방법

오늘과 나중의 호출 흐름은 동일하다.

```text
오늘   테스트 메뉴에서 대상 블록 지정 ─┐
                                      ├─ ApplyHit → Block.TakeDamage와 공 효과 → HitResult
나중   실제 충돌 코드에서 대상 획득 ──┘
```

실제 발사 시작 시 구간을 열고 각 공을 등록한다. 충돌 코드에서 직접 맞은 Block을 얻은 뒤 `ApplyHit`을 호출한다. 여기서 다시 `Block.TakeDamage`를 호출하면 직접 피해가 두 번 적용되므로 충돌 쪽의 별도 피해 호출은 제거한다. 팀원이 요청한 TakeDamage 호출은 효과 시스템 내부에서 수행한다.

충돌 코드는 유효한 결과의 `DirectTargetDestroyed`를 받아 관통 또는 반사를 결정한다. 예를 들어 체력 12인 블록은 공격력 10의 가로 레이저공 직접 피해만으로는 살아 있지만 즉시 레이저 효과로 파괴된다. 따라서 최초 TakeDamage 반환값만으로 반사를 확정하지 않는다. 이후 연결되는 다른 능력이 즉시 대상을 제거할 수도 있으므로 실제 방향 결정 직전 대상 생존 여부도 확인한다.

화염의 미래 피해는 반사 판단을 기다리게 하지 않는다. 전체 발사 구간 종료 시 `EndShot`을 호출한다. 각 공의 개별 복귀와 전체 구간 종료를 구분하는 책임은 후속 발사 및 회수 시스템에 있다.

물리 통합 때 추가로 검증할 항목은 고속 충돌 누락, 하나의 접촉에서 중복 호출, 벽과 블록 구분, 파괴된 블록 통과, 모서리 반사, 여러 공 동시 적중과 전체 회수 종료다. 오늘의 기능 테스트 통과를 물리 통합 완료로 해석하지 않는다.

## 11 기획상 확인 사항

### 화염의 발사 종료 처리

기획서 2.2절은 회수 후 남은 화염 피해를 적용한다고 적고, 4.1절은 발사 구간 종료 시 남은 예약을 취소한다고 적어 서로 다르다. 이번 계획은 세부 규칙인 **4.1절의 예약 취소**를 작업 가정으로 사용한다. 최종 기획 확인이 필요하며, 변경 시 종료 처리와 해당 테스트를 함께 수정한다. 원본 기획서는 수정하지 않는다.

### 감전 대상의 선택 방식

5 × 5 범위에서 최대 3개를 중복 없이 선택하는 규칙은 명시되어 있지만 가까운 순서 또는 무작위라는 기준은 없다. 이번에는 **후보 중 무작위 비복원 선택**을 작업 가정으로 둔다. 선택 함수를 분리해 나중에 우선순위를 바꿀 수 있게 한다.
